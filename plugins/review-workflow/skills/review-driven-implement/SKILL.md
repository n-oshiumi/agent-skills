実装 → テストで品質を担保 → Codex 外部レビュー(**1回だけ**)の流れ。
旧方式の「P0/P1/P2 = 0 まで Codex レビューを反復」は**廃止**。合否はテスト・スクショ確認・E2E で決める。

## Usage

```
/review-driven-implement docs/specs/xxx.md
/review-driven-implement <要件>
```

`$ARGUMENTS` が仕様パス / issue 番号 / 要件文。

## プロジェクト固有設定の読み方(最初に行う)

この skill は全リポ共通の正本(`~/.claude/skills/review-driven-implement/`、Codex は `~/.codex/skills/review-driven-implement`)。
テストコマンド・品質ゲート・固有チェックリスト・学習記録のパスはリポ側にある。次の順で探し、見つかったものを「プロジェクト固有設定」として以降の Phase で使う:

1. `<repo>/.claude/review-driven-implement.project.md`
2. 無ければ旧形式: `<repo>/.claude/commands/review-driven-implement.md` の `<!-- PROJECT:BEGIN -->` 〜 `<!-- PROJECT:END -->`
3. どちらも無ければ固有設定なしとして進める(テスト・品質ゲートのコマンドは CLAUDE.md / package.json / Makefile から特定し、完了報告に「固有設定なし」と書く)

固有設定に書くもの: テスト・品質ゲートの実コマンド / 検証ゲート(UI・E2E)の適用範囲 / 固有チェックリストのパス / 学習記録のパスと作り方 / Codex に渡す追加コンテキスト。共通ワークフロー自体は書かない。

## Phase 1: 準備

- 仕様・受け入れ基準を読み、TodoWrite に登録する。
- 共通チェックリスト(`review-checklist` skill の `severity.md` + `common.md` + 変更するレイヤー)と、末尾の「プロジェクト固有設定」に列挙された知見(review-learnings / knowledge / 固有チェックリスト)を検索・参照し、過去の教訓を実装方針に反映する。

## Phase 2: 実装 + テスト作成

- 実装と**同じ作業で**、触ったコードパスを網羅するユニット・結合テストを追加/更新する。「あとでテスト」は不可。
- バグ修正は回帰テスト必須(修正前に失敗し、修正後に通ることを確認)。
- テストが現実的に書けない箇所は理由を明記し、代替(ロジック抽出してユニット化等)でカバーする。

## Phase 3: 自己レビュー + テストゲート

- 共通チェックリスト(`review-checklist` skill: `severity.md` + `common.md` + 差分レイヤーの references)と固有チェックリスト(プロジェクト固有設定)に沿って自己レビューし、P0/P1 を修正する。**自己レビューのループは最大2回**。
- 該当レイヤーの全テストを実行し、**すべて green** になるまで Phase 2 に戻る(テスト失敗の修正はループ回数に数えない)。

## Phase 4: 検証ゲート(変更種別ごと)

該当するものだけ実施する(適用範囲はプロジェクト固有設定):

- **ロジック系**: Phase 2–3 のユニット・結合テスト網羅 + 全テスト green で pass。
- **UI系**: playwright-cli skill で変更画面のスクリーンショットを撮り、**機能単位で1回にまとめて**ユーザーに提示し、目視確認を待つ。イテレーションごとに何度も確認を求めない。
- **E2E**: **クリティカルパスのみ** playwright-cli で実行し、全部 OK なら pass。E2E を網羅的にしない(網羅はユニット・結合テストの責務。E2E の肥大は flaky 化して別のループ地獄を生む)。

## Phase 5: Codex 外部レビュー(1回固定)

- fresh な Codex(`/codex:rescue` または `Task(subagent_type="codex:codex-rescue")`)で **1回だけ** レビューする。**再レビューはしない**(修正後の確認はテストで行う)。
- 渡す観点は次に限定し、プロンプトに明示する: **仕様の読み違い / セキュリティ / 設計上の見落とし**。スタイル・好み・プロジェクト外の一般論は対象外。
- focus には次の3ブロックを必ず入れる(レビューを1回で終わらせるための宣言。出典: fukuro-automations FUK-179 の学び):
  - `[BLOCKING DEFINITION]` — 何をブロッカーとするかを**先に宣言**する(例: データ破壊・セキュリティ/プライバシーの fail-open・起動不能/ロックアウト・テナント境界破り)。それ以外は non-blocking の follow-up として列挙のみさせる。「指摘ゼロ」を終了条件にしない。
  - `[SCOPE]` — **今回の変更差分に起因する指摘のみ**。既存欠陥はスコープ外とし「未対応負債」として記録だけさせる(対象を広げると自己増殖ループになる)。
  - `[REJECTED]` — 不採用にした指摘を「指摘 → 理由」で渡し、**論拠自体に反論できるときだけ再提起せよ**と条件を付ける(初回は "none yet")。
- **P0/P1 の資格要件**: 「この入力・状態 → この誤動作」という具体的な失敗シナリオを提示できること。**P0 は失敗するテストとして書けるものに限る**。資格を満たさない指摘は P2 以下へ降格して扱う。
- 対応:
  - 資格を満たす P0/P1 → 失敗するテストを書いて修正し、テスト green で完了(Codex に再確認しない)。
  - P2 以下 → 学習記録に残すだけでよい。対応は任意。
- セキュリティ / データ分離 / 破壊的変更に関わる修正は、自動修正せず先にユーザーへ方針確認する。

## Phase 6: 完了

- 品質ゲート(プロジェクト固有設定のコマンド)を実行する。
- 再発し得る Codex 指摘・自己レビューの見逃しは学習記録(プロジェクト固有設定のパス)へ記録する。`/review-learning` があればそれを使い、**観点が一般的(他リポでも通じる)なら `review-checklist` skill の該当 references 末尾「## 候補(レビューで発見)」に、プロジェクト固有ならリポ側チェックリストの候補節に1行追記する**(学びを書きっぱなしにしない。チェックリストに還流して初めて次のレビューが賢くなる)。
- 完了報告: 1. 変更内容 2. 変更ファイル 3. 実行した確認と結果(チェックリスト確認: 読んだ references と指摘/対応を含む) 4. 実行できなかった確認と理由 5. 残リスク。
- コミット / push はユーザーが明示的に依頼した場合のみ。

## 完了条件

- 受け入れ基準を満たしている。
- 触ったコードパスにテストがあり、全テスト green。
- UI 変更はユーザーのスクショ確認済み。E2E 対象はクリティカルパスが pass。
- Codex レビューを1回実施し、資格要件を満たす P0/P1 が 0。
- 品質ゲートが通り、関連ドキュメントが更新されている。
