# backend — API・サービス層・ジョブ・認可・外部連携

## 認証・認可
- [P0] エンドポイント/アクションごとにサーバ側で認証を検証する。「ミドルウェアで守られている」を理由にしない。外部 callback(webhook)を認証ゲートが塞いでいないかも見る
- [P0] 認可はリソース単位で行い、取得/更新/削除のクエリ条件に所有者・テナント識別子を含める。テナントはクライアント入力でなくサーバ側セッションから確定する
- [P0] 管理操作の対象 ID は必ず自スコープに再スコープする(IDOR)。UI で隠した操作もサーバ側で再チェックする(UI の非表示はセキュリティ境界ではない)
- [P0] 一覧取得の権限が個別取得より緩くない(緩い一覧条件で全件列挙できる)。更新可否は更新後の値で判定する(親の付け替えで回避されない)
- [P0] 永続化層へ渡す値は検証済みのものだけ。生のリクエスト全体を流すと主キー・所有者 ID を注入される(mass assignment)
- [P1] フィーチャーフラグ・クライアントの条件分岐を「アクセス制御」に使わない。状態ゲート(要パスワード変更・セッション失効)もサーバ側の処理本体で強制する
- [P1] 状態変更リクエストに CSRF 対策があり、生成系・高コストのエンドポイントにレート制限がある
- [P1] 管理操作の対象が実行者自身のとき資格情報を壊さない。権限主体が 0 人になる操作を止める

## 入出力
- [P0] 金額・通貨・商品はサーバ側で決定し、通貨は最小単位の整数で扱う(クライアントから金額や任意の価格 ID を受けない)
- [P1] 外部入力を境界でスキーマ検証してから使う。検証エラーの既定メッセージをそのままユーザーへ返さない
- [P1] レスポンスはモデルを素で返さず整形層を通し、隠すべきフィールドが漏れず項目が固定される。外部 API の生レスポンスをクライアントへ渡さない
- [P1] エラー応答の body 形とステータスを全経路で統一する(エラー時に 200 を返さない)。例外原文・SQL・スタックトレースを露出しない
- [P1] クライアントが叩くパス・送信キー・参照キーがサーバ側定義と綴りまで一致するか、相手側を実際に読んで確認する(型共有が無い構成ではビルドで検出されない)
- [P1] API 契約の変更(フィールド削除・型変更・必須化)が既存クライアントを壊さない。旧バージョンのクライアントが動き続けるか
- [P1] クライアントに閾値・判定ロジックを配布しない。サーバが確定値・絶対時刻を返す
- [P1] 受信スキーマの表示目的の任意フィールドは局所的に縮退させ、型不一致で全体の parse を落とさない

## 状態遷移・トランザクション・冪等性
- [P0] 状態遷移は条件付き UPDATE + 影響行数で原子的に行う。「SELECT で確認してから UPDATE」の 2 文は競合で壊れる。運用 CLI 経路にも同じ不変条件を掛ける
- [P0] 複数テーブル更新はトランザクションで包む。同時実行があり得る処理は明示的排他(行ロック)を取る
- [P0] トランザクション内で副作用イベント(通知・ブロードキャスト)を発火しない。本体がロールバックしても副作用だけ残る。コミット後に発火する
- [P0] 再実行可能な処理は冪等。差分加算はイベント ID ベースで、集計更新と処理済み ID の記録を同一トランザクションで行う。壊れたとき実数から再集計できる経路があるか
- [P0] webhook は生ボディで署名検証し、イベント ID の重複・順序不定・並行配信で状態が壊れない。進行中状態はスキップし、再試行は終端状態に限る
- [P0] 「処理済み」の印を内容由来の値(内容ハッシュ)で表さない(ABA)。単調増加の版番号を使う
- [P1] 外部サービスの重複排除を自分の冪等性の代わりに使わない。「一度だけ送る」は自分の DB の条件付き UPDATE で担保する
- [P1] lease(奪取可能な排他)は所有トークンで fencing する。TTL が実処理時間より長いか、heartbeat で延長するか
- [P1] 順序不定イベントの記録更新 WHERE は到達し得る全状態を含める。打ち切り状態(リトライ上限・dead-letter)を別経路が無条件に巻き戻していないか
- [P1] 参照系ハンドラに書き込みを足さない。足すなら単一クエリ・副作用フック無し・巻き戻らなくても破綻しない形にする

## 外部 I/O
- [P1] 外部 API・決済・ファイル I/O の失敗を捕捉し適切な応答に変換する(未処理例外の 500 垂れ流し禁止)
- [P1] 一時エラー(5xx・429・接続断)だけ指数バックオフでリトライし、権限(401/403)・対象なし(404)は即失敗にする。拒否されたら同じ間隔で再試行しない
- [P1] 外部 API の成功を HTTP ステータスだけで判断しない。ボディの成否と、次に渡す ID の存在・型を、取り消せない操作の前に検証する
- [P1] タイムアウトは接続だけでなく本文読み取りにも効かせ、専用コードで分類する。単一の上限を規模の違う対象に一律に当てない
- [P1] webhook から外部 API を呼ぶとき応答をその通信で待たせない(応答後実行に逃がす)
- [P1] SSRF: ユーザー指定 URL へのアクセスは DNS/IP 検証・リダイレクト手動処理・プライベート IP 遮断を通した共通経路のみ
- [P1] オープンリダイレクト(相対パス限定)、パストラバーサル、LIKE のワイルドカードエスケープ、raw 出力へのユーザー由来値の未エスケープ連結がない
- [P1] アップロードは MIME/拡張子/サイズを検証し、悪性 SVG/HTML を画像として受けない。保存パスに所有者識別子を含め、非公開データは短寿命の署名付き URL で返す
- [P1] LLM: ユーザー入力をシステムプロンプトに混ぜない、出力はランタイム検証、コスト/トークン上限、ストリーミングの中断・二重送信・終了後の状態確定

## パフォーマンス・キャッシュ
- [P1] N+1・ページネーションなしの全件取得がない。独立したデータ取得は並列化し、逆に対象数ぶん並べて接続プールを食い潰さない
- [P1] キャッシュされた判定の元データを更新・削除する処理は同じキーのキャッシュを破棄する。テナント別データを共有キャッシュしない。購入可否など鮮度が要る判定をキャッシュで行わない
- [P1] 検索条件を追加したら、一覧クエリと件数集計の全経路に同じ条件を適用したか。複数クエリを突き合わせる応答は同一スナップショットで読む
- [P1] 「最初に見た行」から表示値を採る集計に ORDER BY がある
- [P1] 非同期実行される通知/ジョブ内でリクエストコンテキスト(認証ユーザー・URL・セッション)を参照しない。生成時に受け渡す

## 定期ジョブ・無人処理
- [P1] 「処理対象 0 件」を検知する。「成功」の定義を「プロセス正常終了」にしない(前進を示す信号で判定)。アラート指標が常に非ゼロにならない
- [P1] 再実行が収束する(前進した進捗を巻き戻さない)。定義の再適用(upsert)が実行時に書かれる進捗を巻き戻さない
- [P1] 前段がスキップされた経路が後段を無条件に呼んでいないか。「やることが無ければ即終了」ゲートがまだ記録の無い新規対象を弾いていないか

## 候補(レビューで発見)
- [P1] 外部送信ヘルパーが例外を投げず結果に畳んで返す場合、返り値を検査してから「送信済み」フラグを確定する。部分失敗が再送対象から外れない設計にする(love_trinita 2026-09-08)
- [P1] 警告・エラーメッセージの文字列一致(includes)で機械判定しない。判定に使う事実は戻り値に構造(コード・定数)として持たせ、表示用と判定用を分ける(fukuro / wemiro-technical 2026-09-08)
- [P1] 外部 API の応答が読めないとき Content-Type・宣言 content-length と実読長・壊れ方の種別を記録する。JSON パース例外のメッセージをそのまま記録しない(本文抜粋を含むランタイムがある)(clinic-dashboard 2026-09-08)
- [P2] クローラ系: 実サーバの挙動差(HEAD 拒否→GET フォールバック、robots.txt の空 Disallow 等の仕様)を考慮する(wemiro-technical 2026-09-08)
- [P1] バッチの完了をジョブの終了コードやサマリの status だけで判定しない。「やることが無い」早期 return も ok を返す。利用者に見える状態(最終更新・欠測表示)と突き合わせ、早期 return が飛ばすチェックを読む(clinic-dashboard 2026-09-08)
- [P1] 走行中の処理への相乗り(プロセスを増やさない設計)は競合しないとは言えない。外部 API の発行枠・ロック・DB 接続など共有資源を何が消費するかを数える(clinic-dashboard 2026-09-08)
- [P0] 楽観ロックは「版を読む→比較→書く」の3手順で書かない。トランザクションで囲んでも読むだけでは何もロックされず、同じ版の2リクエストが両方通る。版を WHERE に含めた条件付き UPDATE + 影響行数で判定するか、**必ず1行存在する親行**をロックしてから読み直す。対象テーブル自身の範囲ロックは、行が0件のときギャップロックしか取れず(ギャップロック同士は互換)初回作成同士を直列化できない(wemiro-marketing 2026-09-08)
- [P1] 版カラムを新設したら、その版が守る列を更新する全コードパスを grep して1つ残らず版を進める。新しく足した経路だけ見ると、既存経路からの変更が版を動かさず楽観ロックが無効になる。**FK のカスケード(SET NULL / CASCADE)で間接的に変わる列は grep に出ない**ので別に数える。バックグラウンドジョブが触る列を版にしていないかと対で確認する(wemiro-marketing 2026-09-08)
- [P1] 「同じ内容を送り直しても副作用が起きない」を要求する API で、内容が変わらない書き込みでも版を進めていないか。毎回進めると、宣言的に設定を適用し直す運用が他の保持者の版を無意味に無効化する。同一判定は保存側の正規化(MySQL の JSON はキー順を並べ替える)を踏まえて行う(wemiro-marketing 2026-09-08)
- [P1] 冪等性キー・重複排除キーのハッシュに、サーバーが導出した値(スコープ由来の既定値・現在時刻・採番)を混ぜない。「同じリクエスト」の定義が実装都合で変わり、正しい再送が恒久的に失敗する。ハッシュは検証済みのクライアント入力で計算する(wemiro-marketing 2026-09-09)
- [P1] 一括更新の監査ログを「更新対象として選んだ ID」で書かない。`updateMany` の count は件数であって行の集合ではなく、選択と更新の間に別経路が処理した行にも操作者が付く。必ず存在する親行を FOR UPDATE で直列化するか、更新に使った時刻・版を条件に引き直してから書く(wemiro-marketing 2026-09-09)
- [P1] 「この状態のリソースは見せない」を一覧クエリだけで実装しない。個別取得・詳細サービス・汎用更新も同じ条件で 404 に倒す。id を知っていれば読める穴が残る。表示用の「既知の列挙に無ければ既定値へ倒す」正規化は、新しい状態を足した瞬間にその行を別の状態と偽って返す(wemiro-marketing 2026-09-09)
- [P1] 収集フェーズと更新フェーズが分かれるバッチは、更新の WHERE に収集の WHERE をすべて書く。ID と状態だけの再確認では、収集と更新の間に人が条件を変えた行(救済・取り消し・論理削除)まで処理してしまう(wemiro-marketing 2026-09-09)
- [P1] 「切替後に作られた行だけを対象にする」監視・移行判定の境界は、暦日ではなくデプロイした瞬間を入れる。暦日で切ると同じ日のデプロイ前のデータが必ず引っかかり、恒常的な誤検知になる。新しい監視は本番投入直後に1回手で走らせ、出力を読むまでが導入(wemiro-marketing 2026-09-09)
- [P1] ロックを外部呼び出しの外へ出す「予約 → 外部 API → 反映」構成で、予約状態と完了状態を同じ列の同じ値で表さない。予約時点で最終状態を書くと、途中で落ちた行が重複チェックに永久に引っかかり、UI では存在しないリソースの続行を促す袋小路になる。完了の証拠になる列(生成された外部リソース ID)で区別し、予約には失効期限を置く(wemiro-marketing 2026-09-09)
- [P0] 外部 API の必要スコープは、呼ぶメソッドを列挙して1つずつ確認する。「編集系のスコープを1つ取れば編集操作は一通りできる」と仮定しない。不足は「同意は通るが後段の操作だけ 403」の形で出て、再認証しても要求スコープが同じなので恒久ループになる。強い権限(削除系)が必要になる設計は、権限を増やす前にその操作をやめる設計を先に検討する(wemiro-marketing 2026-09-09)
- [P0] 外部 API へ**書き込む**リクエストの形(パラメータ名・型・必須項目)は、モックのテストを保証と見なさない。モックは自分が書いた形を返すだけで、実 API との契約ズレを原理的に検出できない。実 API に一度通すまで「未検証」として扱い、通ったら送信内容の完全一致をテストで固定する。公式ドキュメントに仕様が無く類推した箇所は、残リスクに書くだけで閉じない(wemiro-marketing 2026-09-10)
- [P1] 一覧・集計クエリを足す / 変えたら、**本番相当の行数**で実行計画を取り、全件ソート・ディスクへの溢れ(外部ソート・一時ファイル)が出ていないか見る。開発 DB は行が少なく、どんな書き方でも一瞬で返るので、レビューでも本人の手元でも遅さが可視化されない。悪化は緩やかに進み、ある日リクエストのタイムアウトを跨いで全断になる(clinic-dashboard 2026-09-11)
- [P1] 集約の中の `DISTINCT`(`count(DISTINCT …)` 等)は入力全件のソートを強制する。副問い合わせの `SELECT DISTINCT` へ出すとハッシュ集約を選べる。置き換えるときは `count(*)` ではなく `count(<列>)` にする(集約の DISTINCT は NULL を数えないが `count(*)` は DISTINCT 後の NULL を 1 件として数え、意味論が静かにずれる)(clinic-dashboard 2026-09-11)
- [P1] 1 リクエストが並列に投げるクエリ本数が接続プール上限に近いなら、プールに取得タイムアウトと文のタイムアウトを置く。無いと詰まりが無限待ちになり、リクエストがタイムアウトした後もサーバ側は接続を掴み続けて、後続まで巻き添えにする(clinic-dashboard 2026-09-11)
- [P1] 「昨日まで動いていた」障害でも、直前の変更だけを疑わない。データ量に比例して悪化する経路(全件スキャン・全件ソート・N+1)は、コードが変わらなくても閾値を跨いだ日に落ちる。先に実測(遅いクエリの実行時間・実行計画)を見てから原因を絞る(clinic-dashboard 2026-09-11)
