# common — 全レイヤー共通(常に読む)

## 仕様・完全性
- [P0] 仕様どおりの挙動か(正常系・エッジ・エラー・空状態)。不明確な要件は推測で埋めず確認する
- [P0] 機能が端から端まで完成しているか(利用者側だけでなく管理側の作成/編集/削除まで。片側だけだと整合性が壊れる)
- [P0] 実装前に関連 spec / ADR の「決定」節を読み直し突合したか。実装で判断を変えたら同じ差分で spec を書き戻す
- [P1] 呼び出し先のシンボル・シグネチャが実在し、引数が本番経路で実際に渡るか(テストでだけ渡る・定義だけの引数)。入口から永続化層までデータフローを追う
- [P1] 新しい関数・ジョブ・イベントに呼び出し元/購読者が実在するか grep する(定義は配線の証明にならない)

## 入力と境界
- [P0] 外部入力(リクエスト・webhook・CLI 引数・ファイル名)は境界で検証してから使う。形式だけでなく実在性(存在しない日付等)、手入力の識別子で外部リソースを引くなら引いた結果が意図した対象か(日付・名前)まで見る
- [P0] 識別子・外部入力をパス・キー・シェル・生 SQL・生 HTML に埋める直前に検証/エスケープする(自前 DB 由来でも入口の検証で代えない)。エスケープは出力時に 1 回だけ、HTML 由来の文字列は取り込み時に実体参照を復号して持つ
- [P1] 短い識別子や部分一致で fail-closed 判定を書かない。列挙外の入力の倒れる向きを確認し、甘くする向きの分類(除外・免除・スキップ)は取りこぼしと誤検知のどちらが安全側かを先に決める
- [P1] 同一性判定・ハッシュ・ロックのキーは正規化後の値で行う(大小文字・Unicode・書式の終端)
- [P1] 検出ルール(PII・秘密・スパム)の誤検知を潰したら真陽性が今も検出されるか実入力で確かめ、境界だけを足す。要素種別ごとに中身を見ず return する分岐は、その中の対象を素通りさせる(配置違いの fixture で否定テスト)

## 欠損・既定値・判定の向き
- [P1] 空・未指定・読めない・0・未取得・判定不能を区別し、欠測は null やフラグ+理由で持つ。`?? 0` 等の既定値が「良い方向」(満点・0件・OK)に倒れて要件を黙って破らないか
- [P1] 判定不能時に倒れる向き(fail-safe / fail-open)を明示する。判定関数が例外・空を返したときの呼び出し側を経路で追う
- [P1] 成功応答に期待フィールドが無いのを「正常な 0 件」にしない。渡していない任意パラメータの既定値を確認する(母集団が静かに狭まる)
- [P1] 「失敗なら X が返る」前提の分岐は X が返る条件を実装で確認する(一括処理 API は一部失敗が成功に見える)

## 重複と横展開
- [P1] 同じ判定・変換・定数・数え方を 2 箇所に書かず、正本 1 つを全経路(本番/確認モード・検出/是正・分岐の両側)から参照する。既存の複製を残すなら両方開き実データで突き合わせるテストを置く
- [P1] 共有の定数・config 値(価格・上下限・間隔・閾値)を変えたら、同じキー・値を読む全モジュールを grep して同じ差分で直し、その値が前提の挙動を洗う。稀なフォールバックを主経路にしたらリスクを再評価する
- [P1] 列挙値・役割・語彙・フィールドを足したら、扱う全層・全組み立て経路(保存→クエリ→型→文言→switch)を grep して同時に足す
- [P1] 同型のバグは横展開し、置き換えた識別子・文言は「古い形が 0 件」を grep で確認する。削除の残骸(import・定数・文言・否定テスト)も同じ差分で処理し、直さないものは未対応負債と明記する
- [P1] doc コメントが宣言する不変条件や、表示用の導出条件を入力にする指標定義(基準日・分母)を破る変更は、その更新も同じ差分に含める

## エラーハンドリング
- [P1] 3 分類で見る: A. 未処理(try-catch・非同期・外部呼び出しの失敗処理なし) / B. 伝えない(ログのみ・空 catch・state 未反映) / C. 不適切な表示(技術詳細・例外原文・利用者の言語でない・次の行動が不明・機密)
- [P1] 例外を分類コードに丸めても原因の手掛かりを残す(1 コード 1 原因、失敗した判定は別フィールド)。原因種別(一時障害/権限/対象なし)ごとに文言と取れる行動を分ける
- [P1] 包括 catch が配線ミス(未定義参照・引数不一致)まで飲み込まないか。best-effort の try に失敗源を足すなら「投げたときやらなくなること」を数える。整形済みの例外を上位で包み直さない
- [P1] 失敗を「ログにしか出ない」経路にしない(再確認手段か画面表示が要る)
- [P2] ガードの作動は run サマリ・カウンタにも出す。常時作動する正常系を外すなら、同じ見た目の異常系(スキーマ変更で空等)が別経路で見えるか

## 秘密・機微情報
- [P0] 秘密(鍵・トークン・パスワード・認証なしの URL)をコード・ログ・例外・URL クエリ・コマンド引数・手順書・コミットに載せない。子プロセスへ環境変数の全継承で渡らないか(既存行は差分に出ない)。1 つ見つけたら同じ鍵の隣の経路も潰す
- [P0] 機微情報は「値」「文言(分岐に入った事実が属性を表す)」「文脈」の 3 層で見る。件数・バケットが機微属性に 1:1 対応しないか
- [P1] 機微情報をログから外しても、障害調査に要る非機微の手掛かり(エラー種別)は残す
- [P1] 重要な管理操作(権限変更・削除・課金・公開)に監査ログ(誰が・いつ・何を)を残す

## 時間・並行・上限
- [P1] 条件待ちの繰り返し・有限資源を消費する自動ループに、上限回数・連続失敗の打ち切り・人が止める手段があるか
- [P1] タイムアウト・強制終了で殺されうる処理に、殺されたときの経路(状態確定・stale 判定)があるか
- [P1] 検査と処理の対象が同じか(取ってから検査→取り直して処理は TOCTOU)
- [P1] 閾値は 1 つに 1 役割(異常検知とコスト上限を兼ねない)。率の判定には小分母の下限を置き、根拠は打ち切られていない観測から取る
- [P1] 閾値・再試行を決める前に壊れ方が決定論的かランダムかを確かめ、ランダムなら「N 件まで許容」でなく壊れた対象を記録して個別回収する。同じ結果になる失敗(予算超過)は再試行しない
- [P1] 非同期の二重完了・購読/タイマーの解放漏れ・時間で変わる値の非安全なアンラップ
- [P1] TZ はプロジェクトで 1 つに決め、保存・比較・表示の暦日をずらさない。業務上の順序は時刻でなく単調採番で決める

## 取り消せない操作
- [P1] 複数ステップの外部書き込みは途中失敗の後始末(成功分のロールバック)を持つ
- [P1] 取り消せない操作(送信・課金・公開)の後の記録・計測は、操作の失敗に化けない別モジュールに置く
- [P1] 破壊的・上書き操作は確認を取る。不可逆な操作に戻り経路が無ければ仕様と確認文言に明記する

## コード衛生
- [P1] マージ済みの類似実装と命名・構成・設計を揃える(独自の改良より既存パターン。指摘時は実装例を示す)
- [P2] 不要コード(旧関数・旧ルート・未使用 import/変数・コメントアウト・デバッグ出力)を削除する。認可の甘い旧ルートが残るなら P1
- [P2] マジックナンバーの定数化・設定値のハードコード排除。コメントは「なぜそうしないか」だけ。名前は内容を表す
- [P2] 生成物(バンドル・ミラー・サブモジュール)を手で編集せず正本側を直す
- [P2] スキーマ / API 契約 / 権限モデル / アーキテクチャ判断を変えたら関連ドキュメントと ADR を更新する

## 候補(レビューで発見)
- [P1] 多条件の抽選・探索で確定した結果に、後段のフィルタで1要素だけ差し替える設計をしない。他の条件(距離・一意性)は全体で成立しており、入れ替え候補がほぼ全部条件落ちする。フィルタは候補を生む探索ループに入れ、通った候補にだけ高コストの判定を当てる(lp 2026-09-22: 引き直し 7 候補が距離条件で全滅)
- [P1] 任意の付加情報(アシスト・補足属性)を既存の解決・検証経路に相乗りさせるとき、その失敗が本体(必須データ)全体の失敗・見送りに昇格しないか確認する。付加情報は別に解決し、失敗したら付加情報だけ空で保存して知らせる(love_trinita 2026-09-27: アシスト選手 1 名の名寄せ失敗でスタメン・自軍イベント全体が見送られる経路)
