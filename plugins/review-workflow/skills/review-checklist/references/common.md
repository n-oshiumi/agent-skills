# common — 全レイヤー共通(常に読む)

## 仕様・完全性
- [P0] 仕様どおりの挙動か(正常系・エッジ・エラー状態・空状態)。不明確な要件は推測で埋めずエスカレーションする
- [P0] 機能が端から端まで完成しているか(利用者側だけでなく管理側の作成/編集/削除まで)。片側だけの実装は整合性を壊す
- [P0] 実装前に関連する設計決定(spec / ADR)の「決定」節を読み直し、実装と突合したか。実装で判断を変えたら同じ差分で spec を書き戻す
- [P1] 呼び出し先のシンボル・シグネチャが実在し、パラメータが本番経路で実際に渡るか(テストでだけ渡る引数・定義だけの引数がない)。入口から永続化層までデータフローを追う
- [P1] 新しく作った関数・ジョブ・イベントに呼び出し元/購読者が実在するか grep で確認(定義があることは配線の証明にならない)

## 入力と境界
- [P0] 外部入力(リクエスト・クエリ・フォーム・webhook・CLI 引数・ファイル名)は境界で検証してから使う。形式だけでなく実在性(存在しない日付等)まで見る
- [P0] 外部入力をファイルパス・シェルコマンド・生 SQL・生 HTML に組み込む前に検証/エスケープする
- [P1] 短い識別子や部分一致で fail-closed 判定を書かない。列挙外の入力がどちらへ倒れるかを確認する
- [P1] 同一性判定・ハッシュ・ロックのキーは正規化後の値で行う(大小文字・Unicode 正規化・書式の終端)

## 欠損・既定値・判定の向き
- [P1] 空・未指定・読めない・0・未取得・判定不能を区別する。`?? 0` / `?? ""` が要件を黙って破らないか。欠測は null やフラグ+理由で持ち、事実の主張に変えない
- [P1] 判定できなかったときに倒れる向き(fail-safe / fail-open)が明示的に決まっているか。判定関数が例外・空を返したとき呼び出し側で何が起きるかを経路で追う
- [P1] 欠測の既定値が「良い方向」(満点・0件・OK)に倒れていないか
- [P1] 成功応答で期待フィールドが無いのを「正常な 0 件」にしない(スキーマ異常を区別する)
- [P1] 渡していない任意パラメータの既定値を確認する(母集団が静かに狭まる)

## 重複と横展開
- [P1] 同じ判定・変換・定数を 2 箇所に書かない。正本 1 つを全経路(本番/確認モード、検出/是正、分岐の両側)から参照する。既に複製があるなら両方を開いて確認する
- [P1] 列挙値・役割・語彙に値を足したら、その名前を扱う全層(保存→クエリ→型→文言→switch の網羅性)を grep して同時に足す
- [P1] 同型のバグは横展開する。grep で全出現を洗い「古い形が 0 件」で確認する。直さないものは「未対応負債」として明記する
- [P1] 識別子・文言を置き換えたら旧識別子が 0 件か全文検索する。削除の残骸(import・定数・文言・否定テスト)も同じ差分で処理する
- [P1] モデルにフィールドを足したら、そのモデルを組み立てる全コードパスが新フィールドを読むか確認する

## エラーハンドリング
- [P1] 3 分類で見る: A. 未処理(try-catch 欠如・未処理の非同期・外部呼び出しの失敗処理なし) / B. 捕捉したが伝えていない(ログのみ・空 catch・state 未反映) / C. 表示が不適切(技術詳細・例外原文の露出、利用者の言語でない、次の行動が分からない、機密を含む)
- [P1] 例外を分類コードに丸めるとき原因に辿り着ける手掛かりを残す。1 つのコードが複数原因を兼ねない。原因種別(一時障害/権限/対象なし)ごとに文言と取れる行動を分ける
- [P1] 包括 catch が配線ミス(未定義参照・引数不一致)まで飲み込んでいないか。best-effort の try に失敗源を足すとき「この行が投げたときやらなくなること」を数える
- [P1] 既にユーザー向けに整形済みの例外を上位で包み直さない(原因がすり替わる)
- [P1] 失敗が「ログにしか出ない」経路を作らない。ユーザー起点の再確認手段か画面表示のどちらかが必ず要る

## 秘密・機微情報
- [P0] 秘密(鍵・トークン・パスワード・認証ヘッダなしで叩ける URL)をコード・ログ・例外メッセージ・URL クエリ・コマンド引数・手順書・コミットに載せない。1 つ見つけたら同じ鍵を使う隣の経路も潰す
- [P0] 機微情報(個人情報・病歴等)は「値」だけでなく「文言(その分岐に入った事実が属性を表す)」「文脈」の 3 層で見る。件数・バケットも機微属性に 1:1 対応していないか
- [P1] 機微情報をログから外すとき、障害調査に必要な非機微の手掛かり(エラー種別)まで消さない
- [P1] 重要な管理操作(権限変更・削除・課金・公開)に監査ログ(誰が・いつ・何を)があるか

## 時間・並行・上限
- [P1] 「条件が満たされるまで繰り返す」には終了条件と上限回数を入れる。有限資源を消費する自動ループに総試行上限・連続失敗の打ち切り・人が止める手段があるか
- [P1] タイムアウト・強制終了で殺されうる処理に、殺されたときの経路(状態確定・stale 判定)があるか
- [P1] 検査した結果と処理する結果が同じものか(取ってから検査→取り直して処理は TOCTOU)
- [P1] 間隔・頻度・上限の定数を変えたら「その値だから成立していた暗黙の前提」を洗う。稀なフォールバックを主経路に昇格させたときリスクを再評価する
- [P1] 非同期の二重完了・購読/タイマーの解放漏れがない。時間で変化しうる値への非安全なアンラップをしない
- [P1] タイムゾーンをプロジェクトで 1 つに決め、保存・比較・表示の暦日が端末/サーバ TZ でずれない
- [P1] 順序が業務上の意味を持つなら時刻でなく単調採番で決める

## 取り消せない操作
- [P1] 複数ステップの外部書き込みは途中失敗の後始末(成功分のロールバック)を持つ
- [P1] 取り消せない操作(送信・課金・公開)の後に足す記録・計測は、失敗しても操作の失敗に化けない別モジュールに置く
- [P1] 破壊的・上書き操作はユーザーに確認を取る。不可逆にした操作に戻り経路があるか、無ければ仕様と確認文言に明記する

## コード衛生
- [P1] マージ済みの類似実装(3 件)と命名・構成・設計を揃える。独自の「改良」より既存パターン。指摘時は既存実装例を示す
- [P2] 不要になったコード(旧関数・旧ルート・未使用 import/変数・コメントアウト・デバッグ出力)を削除する。認可の甘い旧ルートが残るなら P1
- [P2] マジックナンバーの定数化、設定値のハードコード排除。コメントは「なぜそうしないか」だけ。名前は内容を表す
- [P2] 生成物(バンドル済み仕様・ミラー・サブモジュール側)を手で編集せず正本側を直す
- [P2] スキーマ / API 契約 / 権限モデル / アーキテクチャ判断を変えたら関連ドキュメントと ADR を更新する。「不要」と判断したなら本当に不要かを確認する

## 候補(レビューで発見)
- [P2] 同じ対象で連続再試行しても再現するからといって対象固有の問題と決めつけない。一定割合のランダム失敗を先に潰してから設計する(clinic-dashboard 2026-09-08)
- [P1] 「N 件までは飛ばして続行、超えたら失敗」型の閾値は、相手がランダムに壊れると成否が運で決まる。閾値を置く前に壊れ方が決定論的かを確かめ、ランダムなら壊れた対象を記録して後で個別回収する形にする(clinic-dashboard 2026-09-08)
