# common — 全レイヤー共通(常に読む)

## 仕様・完全性
- [P0] 仕様どおりの挙動か(正常系・エッジ・エラー状態・空状態)。不明確な要件は推測で埋めずエスカレーションする
- [P0] 機能が端から端まで完成しているか(利用者側だけでなく管理側の作成/編集/削除まで)。片側だけの実装は整合性を壊す
- [P0] 実装前に関連する設計決定(spec / ADR)の「決定」節を読み直し実装と突合したか。実装で判断を変えたら同じ差分で spec を書き戻す
- [P1] 呼び出し先のシンボル・シグネチャが実在し、パラメータが本番経路で実際に渡るか(テストでだけ渡る・定義だけの引数がない)。入口から永続化層までデータフローを追う
- [P1] 新しく作った関数・ジョブ・イベントに呼び出し元/購読者が実在するか grep で確認(定義は配線の証明にならない)

## 入力と境界
- [P0] 外部入力(リクエスト・クエリ・フォーム・webhook・CLI 引数・ファイル名)は境界で検証してから使う。形式だけでなく実在性(存在しない日付等)まで、手入力の識別子で外部リソースを引くなら引いた結果が意図した対象か(日付・名前)まで見る
- [P0] 識別子・外部入力をパス・キー・シェルコマンド・生 SQL・生 HTML に埋める直前に検証/エスケープする。自前 DB 由来でも入口の検証を出口の代わりにしない。エスケープは出力時に 1 回だけ(HTML 由来の文字列は取り込み時に実体参照を復号して持つ。二重だと「&amp;」が画面に出る)
- [P1] 短い識別子や部分一致で fail-closed 判定を書かない。列挙外の入力がどちらへ倒れるかを確認する。判定を甘くする向きの分類(除外・免除・スキップ)は、取りこぼしと誤検知のどちらが安全側かを先に決める
- [P1] 同一性判定・ハッシュ・ロックのキーは正規化後の値で行う(大小文字・Unicode 正規化・書式の終端)
- [P1] 検出ルール(PII・秘密・スパム)の誤検知を潰したら真陽性が今も検出されるかを実入力で確かめ、境界だけを足す。要素種別ごとに中身を見ず return する分岐は、その中にだけ現れる対象を素通りさせる(配置違いの fixture で否定テストを置く)

## 欠損・既定値・判定の向き
- [P1] 空・未指定・読めない・0・未取得・判定不能を区別する。`?? 0` / `?? ""` や欠測の既定値が「良い方向」(満点・0件・OK)に倒れて要件を黙って破らないか。欠測は null やフラグ+理由で持つ
- [P1] 判定できなかったときに倒れる向き(fail-safe / fail-open)が明示的に決まっているか。判定関数が例外・空を返したときの呼び出し側を経路で追う
- [P1] 成功応答で期待フィールドが無いのを「正常な 0 件」にしない(スキーマ異常を区別する)。渡していない任意パラメータの既定値を確認する(母集団が静かに狭まる)
- [P1] 「失敗なら X が返る」前提で分岐を書く前に、X が返る条件を実装で確認する(一括処理 API は全件失敗でしかエラーにならず、一部失敗は成功に見える)

## 重複と横展開
- [P1] 同じ判定・変換・定数・数え方を 2 箇所に書かない。正本 1 つを全経路(本番/確認モード、検出/是正、分岐の両側)から参照する。既存の複製は両方開き、残すなら実データで突き合わせるテストを置く
- [P1] 共有の定数・config 値(価格・上下限・間隔・閾値)を変えたら、同じキー・同じ値を読む全モジュールを grep して同じ差分で直し、その値だから成立していた前提を洗う(表示だけ新値で検証は旧値のまま等)。稀なフォールバックを主経路にしたらリスクを再評価する
- [P1] 列挙値・役割・語彙・モデルのフィールドを足したら、それを扱う全層・全組み立て経路(保存→クエリ→型→文言→switch の網羅性)を grep して同時に足す
- [P1] 同型のバグは横展開し、識別子・文言を置き換えたら grep で「古い形が 0 件」を確認する。削除の残骸(import・定数・文言・否定テスト)も同じ差分で処理し、直さないものは「未対応負債」と明記する
- [P1] doc コメントが宣言する不変条件(「X のときだけ付く」)や、表示用の導出条件を入力にする指標定義(基準日・分母)を破る変更は、それらの更新も同じ差分に含める

## エラーハンドリング
- [P1] 3 分類で見る: A. 未処理(try-catch 欠如・未処理の非同期・外部呼び出しの失敗処理なし) / B. 捕捉したが伝えていない(ログのみ・空 catch・state 未反映) / C. 表示が不適切(技術詳細・例外原文の露出、利用者の言語でない、次の行動が分からない、機密を含む)
- [P1] 例外を分類コードに丸めるとき原因に辿り着ける手掛かりを残す。1 コード 1 原因。どの判定で失敗したかは既存コードで代用せず独立したフィールドで運ぶ。原因種別(一時障害/権限/対象なし)ごとに文言と取れる行動を分ける
- [P1] 包括 catch が配線ミス(未定義参照・引数不一致)まで飲み込んでいないか。best-effort の try に失敗源を足すとき「この行が投げたときやらなくなること」を数える。整形済みの例外を上位で包み直さない(原因がすり替わる)
- [P1] 失敗を「ログにしか出ない」経路にしない(ユーザー起点の再確認手段か画面表示が要る)
- [P2] 安全弁(ガード)の作動は run サマリ・カウンタにも出す。常時作動する正常系を外すときは、同じ見た目の異常系(スキーマ変更で空になる等)が別経路で見えるか確かめる

## 秘密・機微情報
- [P0] 秘密(鍵・トークン・パスワード・認証なしで叩ける URL)をコード・ログ・例外メッセージ・URL クエリ・コマンド引数・手順書・コミットに載せない。秘密を足したプロセスの子プロセスへ環境変数の全継承で渡らないか見る(既存行なので差分に出ない)。1 つ見つけたら同じ鍵を使う隣の経路も潰す
- [P0] 機微情報(個人情報・病歴等)は「値」だけでなく「文言(その分岐に入った事実が属性を表す)」「文脈」の 3 層で見る。件数・バケットが機微属性に 1:1 対応しないか
- [P1] 機微情報をログから外すとき、障害調査に必要な非機微の手掛かり(エラー種別)まで消さない
- [P1] 重要な管理操作(権限変更・削除・課金・公開)に監査ログ(誰が・いつ・何を)があるか

## 時間・並行・上限
- [P1] 「条件が満たされるまで繰り返す」処理・有限資源を消費する自動ループに、上限回数・連続失敗の打ち切り・人が止める手段があるか
- [P1] タイムアウト・強制終了で殺されうる処理に、殺されたときの経路(状態確定・stale 判定)があるか
- [P1] 検査した結果と処理する結果が同じものか(取ってから検査→取り直して処理は TOCTOU)
- [P1] 閾値は 1 つに 1 役割(異常検知とコスト上限を兼ねない)。率で判定するなら小分母の下限を置き、根拠の実測は打ち切られていない観測から取る
- [P1] 閾値・再試行を設計する前に壊れ方が決定論的かランダムかを確かめ、ランダムなら「N 件まで許容」でなく壊れた対象を記録して個別に回収する。同じ結果になる失敗(予算超過)は再試行しない
- [P1] 非同期の二重完了・購読/タイマーの解放漏れがない。時間で変化しうる値への非安全なアンラップをしない
- [P1] タイムゾーンをプロジェクトで 1 つに決め、保存・比較・表示の暦日が端末/サーバ TZ でずれない。順序が業務上の意味を持つなら時刻でなく単調採番で決める

## 取り消せない操作
- [P1] 複数ステップの外部書き込みは途中失敗の後始末(成功分のロールバック)を持つ
- [P1] 取り消せない操作(送信・課金・公開)の後の記録・計測は、失敗しても操作の失敗に化けない別モジュールに置く
- [P1] 破壊的・上書き操作はユーザーに確認を取る。不可逆にした操作に戻り経路が無ければ仕様と確認文言に明記する

## コード衛生
- [P1] マージ済みの類似実装と命名・構成・設計を揃える(独自の改良より既存パターン。指摘時は実装例を示す)
- [P2] 不要になったコード(旧関数・旧ルート・未使用 import/変数・コメントアウト・デバッグ出力)を削除する。認可の甘い旧ルートが残るなら P1
- [P2] マジックナンバーの定数化、設定値のハードコード排除。コメントは「なぜそうしないか」だけ。名前は内容を表す
- [P2] 生成物(バンドル済み仕様・ミラー・サブモジュール側)を手で編集せず正本側を直す
- [P2] スキーマ / API 契約 / 権限モデル / アーキテクチャ判断を変えたら関連ドキュメントと ADR を更新する

## 候補(レビューで発見)
- [P1] 多条件の抽選・探索で確定した結果に、後段のフィルタで1要素だけ差し替える設計をしない。他の条件(距離・一意性)は全体で成立しているので、1要素の入れ替えは候補がほぼ全部条件落ちする。フィルタは候補を生む側(探索ループ)に入れ、通った候補にだけ高コストの判定を当てる(lp corp-batch 2026-09-22: Jev 予審の引き直し 7 候補が距離条件で全滅)
