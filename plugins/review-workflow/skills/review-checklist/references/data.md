# data — スキーマ・マイグレーション・集計・PII

## マイグレーション
- [P0] すべてのスキーマ変更をマイグレーション経由にする。本番で DB リセット・再シード系コマンドを実行する手順にしない
- [P0] cascade delete / FK アクションが意図通りで想定外のデータ消失を招かない。追記専用テーブルに行を書き換える FK アクション(SET NULL / CASCADE)を向けない
- [P0] データ移行・バックフィルをローカルの件数・内容前提で書かない。本番を先に数え、想定と違えば止まる。本番の一括更新前に、その行が関わる取引が進行中でないか確認する
- [P1] up/down が可逆で、既存データへの影響(NOT NULL 追加の既定値・型変更の変換・範囲外値のフォールバック)を同一移行で担保する。破壊的変更は expand → contract
- [P1] 共有環境へ適用済みのマイグレーションを編集しない。採番衝突を全ブランチで確認し、コードとマイグレーションを同じコミットに揃える
- [P1] テーブルを作り直す移行は適用直前に本番の実スキーマと列単位で突き合わせ、前後で件数を数える。本番への手動 DML は独立したクエリでの件数検証で確認する
- [P1] スキーマ変更にテーブル/列コメント・スキーマ文書の更新を同梱する。新規フィールドは既存レコードで破綻しない nullable/既定値設計
- [P2] fail-closed の印(掃除対象)を作ったら、掃除を実行するコマンドを同じ差分で出す

## 制約・索引
- [P1] アプリ層で担保している一意性・1 対 1 に DB 側のユニーク制約があるか。無ければ既存重複の寄せ処理付きで追加する(残す行の選択基準を明記)
- [P1] 検索・絞り込み・ソート・FK・一意制約の列に索引。複合索引は WHERE/ORDER BY の順序に合わせる。本番データ量でフルスキャンにならない
- [P1] 範囲検索で索引列を関数でラップしない。ORDER BY が同名の出力列に解決されていないか。生 SQL に埋める序数をパラメータにしない(型解決で辞書順になる)
- [P2] ポリシー数値の強制層を意図的に選ぶ(アプリ層 = 業務ポリシー、DB 制約 = 絶対下限)

## 集計・欠測
- [P1] 「未収集」と「本当の 0」を区別すべき列を default 0 で潰さない(nullable)。欠測が「0」として集計される JOIN になっていない
- [P1] 欠測フラグを行に持たせる設計は、行そのものが作られないケースを塞ぐ(母集合を計画側から取り、未着手と失敗を分ける)
- [P1] ユニークカウント系のロールアップを下位集計値の単純和で書かない。2 時点の比較は母集団を揃える。評価対象が異なる回どうしの増減を「改善/悪化」と断定しない
- [P1] 集計から除外する条件と「未計測」と表示する条件を二重に書かず同じ判定関数を参照する。集計の定義を変えたらデモ/seed 側も揃える
- [P1] 「現在値のミラー」であるトップレベル列を過去期間の集計に使わない。1 つの列が状態で意味を変えるなら絞ってから集計に渡す
- [P1] 個別行フィルタと上位集約で判定の向きが逆になっていない(1 件だけのテストは通る)
- [P1] 機能が依存する上流データが本番のパイプラインを通って実際に着地しているか数える(API で取れる ≠ DB にある)
- [P2] 埋め込む全件データに LIMIT があるなら、上限到達と 0 件を失敗として扱う。暗黙の件数上限は定数化+コメントで明記する

## 型・時刻
- [P1] 生 SQL に手書きで付けた型が実際の戻り値と合っているか(日時が文字列で返る等)。空データ前提のテストだけで通していないか
- [P1] DB の時刻で大小比較して分岐するとき、アプリへ読み出して渡し直さない(精度が落ちる)。比較は SQL 内で、時刻の書き込みも DB に打たせる
- [P1] 日時の保存・比較・表示でタイムゾーンを一貫させる
- [P1] SQL の入力検証で NULL を明示拒否する(比較ガードは NULL を素通りする)

## 権限・機微データ
- [P0] DB 側にも行レベルのアクセス制御を持ち、API 実装ミス時の最後の砦にする。RLS の上にビューを足したら呼び出し元の権限で評価されるか確認し、別スコープで 0 行になるテストを置く
- [P0] 定義者権限の関数は owner / EXECUTE 権限 / PUBLIC からの REVOKE をセットで扱う。新しい DB ロールは「作る / 名義で作る / 配る」の 3 権限を分けて設計する(ローカルの superuser では差が観測できない)
- [P0] 同じ秘密が複数の表に平文で入っていないか名前で全表を走査する。資格情報の発行経路を足すとき既存経路が何を書いているか読む
- [P0] 公開範囲の広いドキュメント・バケットに機微フィールドを追加しない。非公開バケットにオブジェクト単位のポリシーがあり、他者データが推測アクセスされない
- [P1] 読み取りロールの権限漏れをテストで押さえる。越境できるロールへ権限を足さない(allowlist テストが落ちたら allowlist を広げるのは原則やらない)
- [P1] ID を隠すと決めたら派生値(保存キー・ファイル名・URL・ログ・キャッシュキー)まで数える。DB 行の型をそのままクライアントへ渡さない
- [P1] PII 変換の安全性根拠は入力の性質で決まる(乱数用ハッシュを低エントロピー値に流用しない)。ポリシー文面と実装強度を一致させる
- [P1] 生ログ(未マスク全文)の配信経路に新たな流出経路を作らない

## 語彙・分類
- [P1] 分類語彙を自由文字列で受けない。許可値の正本を 1 箇所に置き、登録経路で照合し、読み取り時も語彙で絞る。値を足したら既存データのバックフィルまでで 1 作業
- [P1] 未知・未分類を既定値へ寄せる分類は、既定値に溜まった件数を定点で数える
- [P2] 並び順をデータ由来の既定値で決めない。順序の正本を 1 つ置き意図を書く。複数ランタイムから読む正本はデータ(JSON 等)に置く

## 候補(レビューで発見)
- [P1] 「今後この条件は検出しない」フィルタを足すときは、既存の永続行がどの経路で終端状態へ遷移するかを追う(既存の「改善したので自動解決」経路が嘘の理由を付ける)(wemiro-marketing 2026-09-08)
- [P1] 状態を戻す処理(ロールバック)の WHERE は、状態を変えた処理の WHERE と同じ集合に限定する(戻す側が広いと、その後に削除・変更された行まで巻き戻す)(wemiro-marketing 2026-09-08)
- [P1] ユニークカウント(count DISTINCT 相当)を新規に書くとき、同系統の既存クエリの欠測フォールバックと突合する(clinic-dashboard 2026-09-08)
- [P1] 状態・区分の列挙に値を足したとき、共通定数(未完了条件など)を直すだけで終わらせない。同じ意図の除外を手書きしている分岐(ステータス別の where 生成など)を grep で数える。既定タブは共通定数を通っても、「すべて」や個別ステータスの分岐から新しい値が漏れる(wemiro-marketing 2026-09-09)
- [P1] unique / PK にカラムを足す migration では、その制約に依存しているコード(重複エラーを捕捉して業務エラーに変換している箇所)を grep で洗う。パーティション化でパーティションキーを unique に足すと、その unique に乗っていた冪等性・重複排除が静かに劣化する(moove 2026-09-09)
- [P1] 外部サービスの設定を読み取って判断する機能は、実データを1件見るまで完成扱いにしない。理想形の fixture だけでテストを組むと、値が直値でなく変数・参照・テンプレートで書かれる一般的な運用を落とす。「見つからない」と「確定できない」を別の状態にしたか(案内が実態と食い違うと利用者が見当違いの作業をする)(wemiro-marketing 2026-09-10)
- [P0] upsert しか経路の無い着地テーブルは「上流で消えた」を表現できない。取り込み元が母集合を全件返す取得系なら、消失の検知と下流(正規化・集計)への伝播を同じ設計で持つ。無いと削除済みデータが集計に残り、件数・KPI が恒久的に過大になる(clinic-dashboard 2026-09-11)
- [P0] 「今回返ってこなかった＝消えた」で削除を判定するなら、0 件応答・スキーマ異常を判定から外す(1 回の空応答で母集合を全消去する)。生存キーは応答そのものから取る。書き込み側の run_id・取得時刻の比較で代用すると、保存に失敗した行が消失と誤判定される(clinic-dashboard 2026-09-11)
- [P1] 論理削除フラグを足したら、その行の状態を進める既存の UPDATE すべて(処理済みマーカー・進捗印)にフラグ条件を足したか grep する。印を先に進める経路が 1 本残ると、削除が「適用済み」と偽られて未反映判定から外れ、上流にもう無いので再取得でも直らない(clinic-dashboard 2026-09-11)
