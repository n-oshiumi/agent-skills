# Spec/Design Multireview — 4レンズ並列セルフレビュー

**PRD・設計Specを、作成コンテキストから独立した4つの専門レンズで叩くレビューゲート。**
外部モデルレビューの実効価値の核は「別モデルであること」ではなく「作成コンテキストからの独立」。これを fresh context の並列サブエージェントで構造的に再現する。

## 正本解決ルール（最初に必ず確認）

- 対象プロジェクトに**固有のチェックリスト正本**（例: Wemiro marketing の `.claude/skills/product-spec-review/references/execution-protocol.md`）があれば、**必ずそちらをレンズ項目の正本にする**。本スキルの汎用チェックリストは正本が無いプロジェクトでのみ使う。
- 実行プロトコル（並列4レンズ・収束条件・3分類・外部レビュー任意化）は常に本スキルが正本。

## 4レンズ

全レンズを PRD・設計Spec の両方で走らせる。対象種別で範囲外の項目は N/A（理由1文）。

| レンズ | 見るもの | PRD時の重点 | 設計Spec時の重点 |
|---|---|---|---|
| **L1 リーン・スコープ** | 目的1文/重複禁止/スリム/Non-Goals/成功指標 | 全項目 | 全項目 |
| **L2 価値・ターゲット** | 本質ジョブ/価値仮説/体験の流れ/ポジショニング | 全項目 | V-1/V-5 の逸脱確認のみ（再分析しない） |
| **L3 UX・信頼性・規約整合** | 認知負荷/結論先出し/状態文言/UI規約/用語 | U-4/U-6 中心（レイアウト未定分は N/A） | 全項目 |
| **L4 実現性・運用・失敗モード** | プレモーテム/異常系/横断関心事/データ確定性/運用 | O-1/O-3/O-4 中心 | 全項目 |

### 汎用チェックリスト（プロジェクト固有正本が無い場合のみ）

判定は全項目 PASS / FAIL / N/A ＋ 証拠（doc該当箇所の引用）。証拠を付けられない指摘は出さない。FAIL には「削る/まとめる/統合する」を第一候補にした具体修正案を添える。

**L1 リーン・スコープ**

| # | 検査項目 | FAIL の例 |
|---|---|---|
| L1-1 | 各機能/画面/データの目的が「誰の・どんな課題を・どう解決」の1文で言えるか | 機能名から始まり課題が無い |
| L1-2 | 同じ目的の既存機能・画面と重複しないか（**既存を実際に列挙して突合**。重複は統合/流用が第一候補） | 棚卸しせず「重複なし」と推測 |
| L1-3 | 「無いと困る」もの以外を足していないか（YAGNI / gold plating。「あると便利」止まりは削る/後回し） | 念のためのタブ・誰も頼んでいない設定 |
| L1-4 | Non-Goals・成功指標（数値/観測可能）・テスト可能な受け入れ基準があるか | 「正しく動くこと」「使いやすく」のみ |
| L1-5 | スコープが膨らむ無限定語（「◯◯等」「改善」「最適化」）を残していないか | 「◯◯等を改善」で範囲無限定 |

**L2 価値・ターゲット**

| # | 検査項目 | FAIL の例 |
|---|---|---|
| V-1 | 機能名要求を額面通り要件化していないか。解くべき本質ジョブ（状況・目的・理由）が代替手段との比較付きで定義されているか | 「◯◯画面が欲しい」がそのまま要件化 |
| V-2 | 誰がどんな状況・頻度で使うかが実装判断に足りる解像度か | 利用者が「ユーザー」としか書かれていない |
| V-3 | 価値仮説が具体か（どのペインをどう解消するか。「なくなったら困る」構造か）。形式的な記入で終わっていないか | 効能が「便利になる」のみ |
| V-4 | 使用前・中・後の体験が描けているか。特に**使用後の次の行動**と摩擦ポイント | 数字を見せて終わり・次の行動が無い |
| V-5 | プロダクトのコアバリュー・既存機能内の位置づけと整合するか。新たに生む摩擦・課題の検討があるか | 位置づけ不明の孤立機能・副作用未検討 |

**L3 UX・信頼性・規約整合**

| # | 検査項目 | FAIL の例 |
|---|---|---|
| U-1 | 初見の非専門ユーザーの認知負荷が最小か（画面数・選択肢・指標数・専門用語） | 初見で選択肢が多く「むずい」 |
| U-2 | 結論先出しか。数値に意味付け（比較基準・単位・凡例）があり「この数字は何？」にならないか | 「+5.6」が何か画面から分からない |
| U-3 | 見た後に取る行動への導線があるか（行き止まり画面の禁止） | 分析結果を出すだけで次の一手が無い |
| U-4 | 空・ゼロ件・エラー・ロード中の表示文言が定義され、ユーザー向けは平易な言葉か | 異常時の表示が未定義・内部用語が露出 |
| U-5 | プロジェクトのUIデザインガイドライン・規約に沿っているか | 独自の色・コンポーネント体系を発明 |
| U-6 | 既存の用語集・ナビ体系・情報構造と矛盾しないか | 同じ概念に別の名前・ナビ体系と衝突 |

**L4 実現性・運用・失敗モード**

| # | 検査項目 | FAIL の例 |
|---|---|---|
| O-1 | プレモーテム: 「リリース半年後に失敗していた」原因を1つ以上具体的に描き、その失敗モードへの手当が仕様にあるか | 失敗モードの検討が無い |
| O-2 | データ欠損・同期失敗・権限なし・期限切れ等の異常時に何を表示するか定義されているか | 同期失敗が無音で 0 表示になる |
| O-3 | プロジェクトの横断関心事（認証/権限・課金/プラン・キャッシュ・デモ/テスト環境等）との相互作用を確認したか | 新モデルがデモ環境・権限体系に非対応 |
| O-4 | 表示データの鮮度・確定性（未収集期間・遅延・タイムゾーン境界）が仕様に織り込まれているか | 未収集の直近日を含む窓で過小表示 |
| O-5 | handoff（API/UI境界・Issue粒度）が実装者が判断できる粒度か。リリース後の運用（監視・問い合わせ）が回るか | 受け入れ基準が曖昧・監視不能な自動化 |

### 優先度（汎用）

| 優先度 | 対象 |
|---|---|
| **P0（着手前に要解消）** | 目的が言えない（L1-1）/ 既存と重複（L1-2）/ 明確に過剰（L1-3）/ 本質ジョブ不一致（V-1）/ プレモーテム不能（O-1） |
| **P1（要修正）** | 価値仮説が形式的（V-3）/ 数値の意味不明（U-2）/ 異常系未定義（O-2）/ データ不確定（O-4）/ Non-Goals・成功指標なし（L1-4） |
| **P2（改善推奨）** | 認知負荷・用語整合・導線・削減検討漏れ 等 |
| **P3（任意）** | 表現・軽微 |

## 実行プロトコル

### Step 1: 準備

1. 対象doc（PRD or 設計Spec のパス）と種別を確定する。
2. 正本解決ルールでチェックリスト正本を決める（プロジェクト固有 or 本スキル）。
3. プロジェクトにレンズ別の参照正本（UIガイドライン・用語集・codebase map 等）があれば、レンズごとに渡すパスを揃える。

### Step 2: 並列4レンズレビュー

`Task(subagent_type="spec-design-reviewer")`（plugin 経由で使っている場合は `review-workflow:spec-design-reviewer`）を **4つ、1メッセージで並列発行**する（1レンズ=1エージェント。逐次実行しない）。各プロンプトの骨子:

```
対象: <docパス>（種別: PRD / 設計Spec）
担当レンズ: <L1〜L4 のうち1つ>（担当項目: <ID列挙>）
チェックリスト正本: <正本パス>（担当レンズのセクションだけ読む）
参照正本: <このレンズが判定に使うプロジェクトdocのパス列挙>
手順:
1. 正本の判定原則と担当レンズの項目を読む。
2. 参照正本と対象docを読む。[L1のみ] 既存のナビ/画面/機能を実データで棚卸しして列挙する。
3. 担当項目すべてに PASS/FAIL/N/A ＋ 証拠（doc該当箇所の引用）を付ける。
4. FAIL には P0〜P3 と「削る/まとめる/統合する」を第一候補にした具体修正案を添える。
出力: 判定表 → 発見（優先度順） → 削減・統合提案 → レンズVERDICT（pass / fail）
あなたはこの doc の作成者ではない。擁護せず、反証してから判定せよ。
証拠を付けられない指摘・理論上のみの指摘は出さないこと。
```

### Step 3: 統合と指摘の3分類

メインセッションで4結果を統合する:

1. 重複指摘をマージし、レンズ間で矛盾する指摘は根拠の強い方に裁定する（裁定理由を1文残す）。
2. 各指摘を3分類する:
   - **(a) 採用** — doc を更新し「採用」と記録する。
   - **(b) 不採用** — 当初指示の本旨と不一致 / レビュアーが文脈・既存制約を誤解 / 過剰要求・スコープ拡張 / 既存の決定事項と矛盾、のいずれかに該当する場合。理由を記録する。
   - **(c) ユーザー確認** — 当初指示と矛盾する・スコープを大きく変える・判断できない場合。AskUserQuestion で指摘原文＋自分の評価＋推奨を添えて確認する。

### Step 4: 収束

- **ready 判定: 全レンズで P0/P1 = 0**（P2/P3 は記録のみで ready を妨げない）。
- 反映後の再レビューは **FAIL が出たレンズのみ** 再走する。再走は最大2回（初回含め計3ラウンド）で打ち切る。
- 3ラウンドで解消しない P0/P1 は、AskUserQuestion（推奨付き）でユーザー裁定に上げる（残す/削る/差し戻す）。理論上のみの指摘は打ち切ってよい。
- 完了時に VERDICT（prd-ready / design-ready / 要修正）とレンズ別 pass/fail・ラウンド数を明示する。

## 外部モデルレビュー（Codex 等）— 任意・最大1回

既定では実施しない。次の場合のみ:

1. **ユーザーが明示要求**したとき — 必ず実施する。
2. **高リスク変更**（課金・権限・データ削除・既存画面/機能の置換や廃止に触れる）のとき — 実施を**推奨として提案**する（勝手に実行しない）。
3. **3ラウンド後も P0 の裁定が割れる**とき — 第三者裁定として提案する。

実施時も1回で打ち切り、指摘は Step 3 の3分類で処理する。再レビューはしない。

## アンチパターン

- 4レンズを1つのセッションで順次演じる（作成コンテキストが全観点を汚染する。必ず並列サブエージェント）。
- 証拠なしの FAIL・「全体的に問題なし」の一括判定。
- P2/P3 を理由に ready を止める。3ラウンド超のレビューループ。
- 汎用チェックリストとプロジェクト固有正本の二重判定（正本は常に1つ）。
